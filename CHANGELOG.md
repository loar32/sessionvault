# Changelog

## v0.1 — 2026-10-03

- Отдельная учётка `vault` и закрытая папка хранения с ACL: обычные учётки не видят список файлов, не читают данные и не меняют права.
- `sessionvault setup`, `import-tdata` (перенос, без копии), `run telegram` (запуск Telegram от `vault`, окно на рабочем столе пользователя), `status`.
- `access-check` — проверка защиты: чтение файлов, смена прав, чтение памяти процесса.
- Автотест в Hyper-V (`tools/vm`): ВМ создаётся скриптом, защита проверена на настоящем Telegram, утечек 0.
- Ограничение: защита работает против процессов обычной учётки; процесс от администратора её обходит.

## v0.2 — 2026-10-03

- Данные приложения шифруются: на диске только `data.enc` (AES-256-GCM) и `vault.json`. Ключ данных (DEK) обёрнут ключом из мастер-пароля (Argon2id, 128 МБ, 3 прохода).
- `import-tdata` спрашивает мастер-пароль и сразу шифрует; `run` расшифровывает, запускает приложение, а после его выхода шифрует обратно.
- Дошифровка остатков: после сбоя при следующем `run` открытые данные возвращаются в архив.
- Если `sessionvault` завершён, приложение завершается вместе с ним (job object), чтобы не работать с открытыми данными без наблюдателя.
- Ключи закрепляются в памяти (VirtualLock) и обнуляются; запись `data.enc` атомарная, с Sync.
- Проверка параметров Argon2id из `vault.json` до вывода ключа; повторный запуск того же профиля блокируется.
- Тесты: nonce уникальны, подмена шифротекста и неверный ключ отклоняются, tar не выпускает за пределы папки; автотест в ВМ проверяет шифрование, закрытие, сбой и неверный пароль.
- Известно: `log.txt` Telegram остаётся вне `tdata` открытым; полные права `vault` на папку профиля — к v0.3.

## v0.3 — 2026-10-03

- Служба Windows от SYSTEM (`sessionvault service`), бинарник в Program Files. Pipe команд `\\.\pipe\SessionVault` доступен только SYSTEM и основной учётке; протокол — две команды, `status` и `run <профиль>`, без аргументов и без выдачи данных. Всё остальное отвергается, число соединений ограничено.
- Мастер-пароль вводится в окне, которое запускает сама служба от SYSTEM в сессии пользователя; пароль идёт по отдельному pipe, закрытому для обычных учёток, и проверяется по PID окна. Три попытки, затем отказ.
- Автоблокировка: через N минут бездействия (по умолчанию 15) ключи стираются из памяти службы. Пока приложение запущено, не блокируется.
- Если служба упала или остановлена, приложение гаснет вместе с ней (job object); открытые данные дошифровываются при следующем запуске. Служба перезапускается сама, аварии пишутся в `service.log`.
- Права профиля сужены: у `vault` доступ только к рабочей папке `work`; `vault.json`, `data.enc`, маркеры доступны только администраторам и SYSTEM. В `work` лежит и `log.txt` Telegram, поэтому он тоже шифруется.
- Профили приложений — JSON в ProgramData (`profiles\telegram.json`), запись только SYSTEM и администраторам.
- Трей: иконка зелёная (заблокировано), оранжевая (открыто), серая (служба недоступна); пункт меню запускает Telegram.
- Установщик Inno Setup (`SessionVaultSetup.exe`) и команды `install` / `uninstall`. Установка отказывает, если основная учётка — администратор, и откатывает уже сделанное при ошибке. Удаление сначала расшифровывает данные и возвращает `tdata` на прежнее место владельцем-пользователем; при неверном пароле или ошибке не удаляется ничего.
- `import-tdata` сам находит `tdata` пользователя и откатывает перенос при ошибке.
- Основной бинарник собирается как GUI-приложение (`tools/build.ps1`), командные режимы подключаются к консоли.
- Автотесты в ВМ: служба (окно пароля, автоблокировка, сбой службы, пробы pipe), трей и установщик (установка, импорт, запуск из трея, удаление).
- Известные ограничения: пароль в окне виден кейлоггеру в сессии пользователя (до Windows Hello); подпись Telegram.exe не проверяется. Подробности — в README.

## v0.4 — 2026-10-03

- Приманки: на прежнем месте `tdata` (в профиле пользователя) служба кладёт папку со структурой tdata и случайным содержимым, раз в 6 часов пересоздаёт её. Чужую папку на этом месте не трогает.
- Аудит чтения: служба включает политику «Файловая система», ставит SACL на приманку и подписывается на события 4663 (EvtSubscribe, без опроса).
- Реакция на чтение приманки посторонним процессом: приложения закрываются, данные шифруются, ключи стираются, окно тревоги со звуком (процесс, путь, SHA-256, время), запись в `alerts.log`, красная иконка трея (`status` отвечает `alarm`).
- Белый список процессов в `config.json` (`decoy_allow`): путь с `*` как один каталог и издатель подписи (WinVerifyTrust офлайн); по умолчанию поиск Windows и Defender.
- Команда `sessionvault alerts` (от администратора): состояние аудита и журнал тревог. `access-check -decoy` читает приманку как стилер.
- Удаление убирает приманку перед возвратом данных и возвращает политику аудита, если её включили мы.

## v0.4.3 — 2026-10-04

- Формат хранилища версии 2: версия, соль и параметры Argon2 входят в проверку обёрнутого ключа (AAD), а `data.enc` получил заголовок с номером записи, который тоже входит в AAD. Откат `data.enc` на старую копию обнаруживается и отклоняется. Хранилища v1 переводятся в v2 при первой разблокировке; старый `data.enc` читается до первой записи.
- Новая команда `sessionvault restore-backup <профиль>` (от администратора, нужен мастер-пароль) возвращает предыдущий архив из `data.enc.bak`.
- Ограничение частоты `run`: не чаще одного запроса в 2 с; после отказа или закрытия окна пароля новое окно не раньше чем через 10 с. При разблокированном хранилище запуск без пароля работает как раньше.
- Права `vault` на рабочий стол снимаются после выхода приложения.
- Служба принимает preshutdown и сообщает WaitHint: при выключении Windows данные успевают зашифроваться.
- Учётке `vault` запрещены сетевой и удалённый вход (SeDenyNetworkLogonRight, SeDenyRemoteInteractiveLogonRight); при удалении права снимаются.
- Каталоги Windows берутся через SHGetKnownFolderPath, а не из переменных окружения. `config.json` пишется атомарно под общей блокировкой.

## v0.5 — 2026-10-04

- Защита браузеров Chrome, Edge и Brave: `sessionvault protect <браузер>` создаёт новый защищённый профиль (запуск от `vault`, профиль зашифрован, кэши в архив не попадают), удаляет прежний профиль основной учётки после подтверждения и ставит на его место приманку в стиле Chromium. Проверено на Edge в ВМ: запуск, сохранность профиля между запусками, шифрование при закрытии, тревога по приманке, отсутствие ложной тревоги от обычного Edge.
- Меню трея строится по списку защищённых приложений (новая команда `list` в протоколе службы: отдаёт только имена профилей).
- Учётка `vault` получает право создавать именованные объекты в `Local\` сеанса пользователя на время работы приложения (и теряет его после выхода). Без этого Chromium не стартует под `vault`: «Failed to create a ProcessSingleton».
- Профиль приложения расширен: название, прежнее место данных, исключения из архива, вид приманки. Профиль Telegram старого формата читается как раньше. JSON с BOM (его добавляют PowerShell и некоторые редакторы) принимается.
- Размер архива ограничен 1 ГиБ: при превышении шифрование отменяется с понятной ошибкой.
- Ограничение частоты запуска и пауза после отказа в пароле считаются по каждому приложению отдельно.
- `import-tdata` остаётся; `protect telegram` делает то же самое.

## v0.5.1 — 2026-10-04

- Chrome и Brave проверены в ВМ так же, как Edge: запуск от `vault`, профиль между запусками, шифрование при закрытии, приманка, тревога, отсутствие ложной тревоги от обычного браузера, `access-check` при работающем браузере.
- Служба больше не ставит аудит на путь приманки, если на нём (или выше) ссылка или junction: раньше такой путь уводил SACL на чужую папку.
- Удаление программы отказывается возвращать данные, если на пути прежнего профиля ссылка или junction (раньше администратор переносил и удалял файлы по пути из профиля пользователя без этой проверки).
- `protect` повторно проверяет путь перед переименованием прежнего профиля; браузер ищется и в `Program Files`, и в `Program Files (x86)`.
- Кэши исключаются из архива по шаблону для любого профиля браузера (`Profile 1` и т. д.), а не только `Default`.
- Паника в обработчике запроса не останавливает службу; журнал не растёт от запросов `run` с несуществующими именами.

## v0.6 — 2026-10-04

- Хранилище блокируется по событиям Windows: блокировка сеанса, выход из системы, сон. Запущенное приложение не теряет ключ: блокировка выполняется сразу после его выхода. Таймер бездействия теперь 4 часа по умолчанию (в уже установленных копиях остаётся прежнее значение из `config.json`), отрицательный `idle_minutes` его выключает.
- Блокировка хранилища также при смене пользователя и отключении сеанса (RDP). Откат мер ОС не принимает из `config.json` значения вне диапазона.
- Белый список приманки: проводник, поиск Windows (протокол и фильтры), доп. процессы Defender и сторонние антивирусы с проверкой подписи. Меньше ложных тревог, окно тревоги не изменилось.
- Тихие системные меры: `sessionvault harden` включает шифрование файла подкачки, отключает гибернацию и дампы памяти; установщик предлагает это галочкой, удаление возвращает прежние значения.

## v0.7 — 2026-10-04

- Вход через Windows Hello: хранилище открывается отпечатком, лицом или PIN в системном окне вместо мастер-пароля. Включается пунктом трея «Включить вход через Windows Hello» (мастер-пароль нужен один раз), отключается `sessionvault hello disable [профиль]`. Мастер-пароль остаётся запасным способом: отмена Hello или сбой открывают прежнее окно пароля.
- Устройство: второй слот в `vault.json` (тот же ключ данных, обёрнутый ключом из подписи Hello), проверка подлинности слота привязана к хранилищу и запросу; Hello вызывается напрямую через WinRT без новых зависимостей; помощник работает под учётной записью пользователя и отдаёт подпись службе по закрытому pipe. Формат хранилища v2, старые файлы читаются.
- Новая команда pipe `hello <профиль>` (как `run`: только имя профиля, лимиты частоты те же).
- Тесты: слот Hello (круг, чужой секрет, подмена запроса, отключение), Hello на чекпойнте ВМ с PIN (`tools/vm/prepare-hello.ps1`): вход без пароля, запасное окно пароля после отмены.

## v0.7.1 — 2026-10-04

Ревизия v0.7 (Windows Hello): найденное исправлено.

- Если жест Hello не сделан за ~70 секунд, помощник отменяет операцию и закрывает окно Hello (раньше окно оставалось висеть на экране после того, как служба убивала помощника), затем открывается окно мастер-пароля.
- Pipe Hello открыт учётной записи пользователя, поэтому подключиться раньше помощника мог любой её процесс и сорвать вход через Hello. Служба теперь отбрасывает чужие подключения (проверка PID) и ждёт нужное, а не отказывается целиком.
- Пункт трея «Включить вход через Windows Hello» сначала проверяет, настроен ли Hello (без жеста), и только потом просит мастер-пароль; раньше пароль вводился зря.
- Повторный ввод пароля (включение Hello при разблокированном хранилище) стирает прежний ключ из памяти, а не оставляет его.
- Лимит ответа помощника увеличен, чтобы не ломать вход при другой длине подписи.
- Пробы `hello ...` добавлены в `access-check` (мусорные и чужие запросы отклоняются).
- Тесты: Hello в ВМ теперь включает таймаут (окно закрывается) и включение через службу с созданием ключа и вводом мастер-пароля.

## v0.8 — 2026-10-04

- Ссылки в защищённом браузере: `sessionvault open <ссылка>`. Заперто — окно разблокировки (Hello или пароль), затем браузер стартует сразу со ссылкой; браузер уже запущен — ссылка открывается вкладкой в нём без пароля. Браузер: первый из Chrome, Edge, Brave или `link_profile` в `config.json`.
- Новая команда pipe `open`: ссылка идёт второй строкой и проходит строгую проверку (только http/https, печатный ASCII, без пробелов, кавычек и обратных слэшей, до 2048 байт, обязательна схема, поэтому она не может быть параметром браузера). Ссылка попадает только в командную строку браузера; данные из службы по этой команде не выдаются, лимиты частоты те же.
- Регистрация системным обработчиком http/https не делается: Windows 11 не даёт менять браузер по умолчанию без участия пользователя.
- Тесты: разбор `open` и проверка ссылок (флаги, file:, javascript:, кавычки, юникод, длина); автотест в ВМ открывает ссылку при запертом и запущенном браузере и отклоняет не-http(s); мусорные пробы `open ...` в access-check.

## v0.9 — 2026-10-04

«Тише»: меньше фоновой работы, без изменения защиты. Нумерация идёт подряд после v0.8.1; пункты плана проекта (помощник безопасности и далее) — в следующих версиях.

- Трей опрашивал службу каждые 2 секунды круглосуточно. Теперь раз в 10 секунд, а 2 секунды только минуту после действия пользователя (запуск приложения, включение Hello), чтобы иконка не отставала. Вызовов pipe в простое примерно 6 в минуту вместо 30.
- Служба проверяла приманки и аудит каждые 30 секунд. Теперь раз в 5 минут (приманка и так обновляется раз в 6 часов). После `protect` и `import-tdata` CLI просит службу проверить сразу. Для этого CLI администратора взводит именованное событие `GlobalSessionVaultSync` (доступно только SYSTEM и администраторам, ничего не передаёт, служба ждёт его без опроса): pipe закрыт для администратора, а протокол остаётся прежним.
- Тесты: автотест в ВМ: приманка появляется сразу после `protect`, а не через 5 минут.

## v0.9.1 — 2026-10-04

Ревизия безопасности v0.9.

- Приманка собиралась прямо в папке пользователя, а служба от SYSTEM меняла в ней владельца и права. Пользователь мог в этот момент подменить подпапку ссылкой (junction) и увести смену владельца на системные файлы. Теперь приманка собирается в закрытой папке службы, права выставляются там и готовая папка переносится на место целиком.
- Возврат данных при удалении программы (`GiveToUser`) больше не меняет права по ссылкам и junction внутри данных приложения.
- Ссылка или junction внутри данных приложения срывала шифрование при каждом выходе (архив отказывался брать «неподдерживаемый тип», данные оставались расшифрованными). Теперь такие элементы пропускаются, файлы за ссылкой не затрагиваются.
- Хэш exe при тревоге не считается, если процесс запущен не с локального диска: иначе exe с сетевой шары заставил бы службу обратиться к чужому серверу.
- Журналы `service.log` и `alerts.log` ограничены мегабайтом (прежний уходит в `.1`).
- В README записано, что процесс вашей сессии может открыть ссылку в защищённом браузере командой `open`.
- Отложено: возврат данных при удалении всё ещё идёт по путям (взломанное приложение под vault могло бы подменить папку в момент удаления), аудит приманки по пути пользователя; запись SACL следует NoReparse, но гонка остаётся.

## v0.14 — 2026-10-05

Тихий журнал чтения памяти.

- Служба ставит аудит Windows (объекты ядра и выдача дескрипторов, успехи и отказы) на процессы защищённых приложений и пишет в `memory.log`, какой чужой процесс читал, писал или пытался прочитать их память (отказанные попытки с пометкой): время, учётка, программа, права. Окон и тревог нет. Свои процессы (`vault`, служба, SYSTEM) не записываются, повторы одного процесса с теми же правами сливаются на минуту, файл ротируется.
- Аудит ставится на процессы из job-объекта при запуске приложения (сразу и через 5 секунд, когда появятся потомки браузера) и при опросе статуса треем, не чаще раза в 5 секунд и только пока приложение запущено. Новых таймеров нет.
- В отчёте `check` пункт «Чтение памяти приложений» (справка, итог не меняет). Прежние значения политик аудита сохраняются и возвращаются при удалении программы.
- RAM-диск не делается: в Windows нет встроенного, а драйвер (ImDisk, WinFsp) нарушает принцип «один бинарник без зависимостей». Записано в «Границы защиты».
- Тесты: юнит-тесты (разбор события, фильтр и слияние повторов, пункт отчёта), в ВМ-тесте чтение памяти процесса `vault` из обычной учётки попадает в журнал без тревог.
